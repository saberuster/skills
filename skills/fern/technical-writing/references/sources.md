# Sources and adopted principles

This is a source index for maintaining the skill, not a requirement to read
every source or browse the web for each documentation task. The skill
synthesizes these resources in its own words; it does not reproduce their
manuals. Consult a relevant original when revising guidance or resolving a
source-specific question.

| Source | Adopted principles |
| --- | --- |
| Google: [Technical Writing](https://developers.google.com/tech-writing/overview), [Developer documentation style guide](https://developers.google.com/style) | Define audience and scope; organize useful explanations, examples, and visuals; use clear terminology and accessible presentation. |
| Google: [Software Engineering at Google, Chapter 10: Documentation](https://abseil.io/resources/swe-book/html/ch10.html) | Treat documentation as maintained engineering work; distinguish document purposes and ownership; explain decisions and tradeoffs. |
| Microsoft: [Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/), [Microsoft Learn style quick start](https://learn.microsoft.com/en-us/contribute/content/style-quick-start) | Put useful information first; organize around reader tasks; make prose easy to scan and localize. |
| OpenAI: [What makes documentation good](https://developers.openai.com/cookbook/articles/what_makes_documentation_good) | Use informative headings, early conclusions, clear references, and self-contained examples. |
| OpenAI: [Cookbook contributing guide](https://github.com/openai/openai-cookbook/blob/main/CONTRIBUTING.md), [Developer quickstart](https://developers.openai.com/api/docs/quickstart) | Make examples reproducible; state dependencies and inputs; give readers a short path to a visible result. |
| Anthropic: [Doc Co-Authoring Workflow](https://github.com/anthropics/skills/blob/main/skills/doc-coauthoring/SKILL.md) | Gather necessary context, organize and revise iteratively, and test comprehension with a reader who lacks conversation context. |
| GitHub: [Best practices for GitHub Docs](https://docs.github.com/en/contributing/writing-for-github-docs/best-practices-for-github-docs), [Combining multiple content types](https://docs.github.com/en/contributing/style-guide-and-content-model/about-combining-multiple-content-types) | Identify audience and reader outcome; select fitting content types; combine clearly organized sections when they serve the same reader. |
| GitLab: [Documentation topic types](https://docs.gitlab.com/development/documentation/topic_types/), [Task topics](https://docs.gitlab.com/development/documentation/topic_types/task/), [Troubleshooting topics](https://docs.gitlab.com/development/documentation/topic_types/troubleshooting/), [Documentation style guide](https://docs.gitlab.com/development/documentation/styleguide/) | Distinguish explanation, actions, reference, and diagnosis; state prerequisites and results; preserve searchable errors; keep edits reviewable. |
| Diataxis: [Framework](https://diataxis.fr/), [Workflow](https://diataxis.fr/how-to-use-diataxis/); Canonical: [Adoption of Diataxis](https://canonical.com/blog/diataxis-a-new-foundation-for-canonical-documentation) | Match tutorials, how-to guides, reference, and explanation to different reader needs; improve existing content through those distinctions. |
| AWS: [Architectural decision record process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html) | Record decision context and consequences; make status and supersession explicit; retain useful historical reasoning. |
| pstack: [Technical Writing](https://github.com/cursor/plugins/blob/00b14f1df36b32a8dd1529324a3a459f6563b127/pstack/skills/technical-writing/SKILL.md) | Use ordinary, precise language and actual project terms; make actions clear; remove words that add no meaning. |

Follow the project's language, conventions, and authority. Source-specific brand
voice, grammar rules, document layouts, fixed counts, style thresholds, tools,
and approval procedures are not universal requirements.

OpenAI's good-documentation article is archived; use it for writing principles.
The Developer quickstart illustrates a finished document. Verify current product
setup, code, models, and contribution policies before reusing them.
