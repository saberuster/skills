# Development and validation

Use the [development environment](../README.md#development) from the repository
root. See [AGENTS.md](../AGENTS.md) for maintenance instructions. The
[validation layers](validation.md) define repository-wide selection, local
Docker execution, CI triggers, result states and coverage limits.

## Python validation entrypoints

The public launcher supports `python scripts/run_validation.py` and
`python -m scripts.run_validation` from the repository root. Direct script
execution imports sibling helpers; package execution uses relative imports.
The Docker unittest subprocess uses `python -m scripts.validation_ci`, so the
repository root remains importable when discovered tests import `scripts`.
No global `PYTHONPATH` configuration is required.

Python places the script directory on `sys.path` for `python scripts/file.py`,
but places the current directory there for `python -m scripts.file`.
Test discovery adds the tests directory, not the repository root. Consequently,
changing only a subprocess working directory cannot repair a missing package
root. Imports must also distinguish script and package execution explicitly:
an unrelated installed `scripts` namespace can raise `ImportError`, which a
`ModuleNotFoundError` fallback does not catch. See the
[Python command-line reference](https://docs.python.org/3/using/cmdline.html#interface-options).

## Agent support CI

The package targets Codex's local skill format. The
[agent support workflow](../.github/workflows/agent-support.yml) checks real CLI
discovery for Codex and Claude Code in temporary projects. It checks packages at
`skills/<name>/` and `skills/<collection>/<name>/`, including `fern`,
`image-generation`, `blender`, `godot`, and `meta`. Each package
is copied into an isolated client directory under its own skill name;
collection directories are not installed as skills.
This is not a claim of successful task execution or automatic selection in
every interface.

| Check | Coverage |
| --- | --- |
| Validate package | Metadata, Markdown, local links, text hygiene, and checker regression tests |
| Codex discovery | `skills/list` returns each copied skill with its expected name, description, path, enabled state, and no load errors |
| Claude Code discovery | SDK initialization lists each copied skill's name and description as an available command |
| Model behavior | Separate affected/full workflows run explicitly requested synthetic agent cases; discovery itself sends no model prompt |

Pushes, pull requests, and manual runs check pinned clients. A weekly run also
checks the latest published Codex package and Claude SDK with its bundled CLI;
manual runs can enable the same latest-version checks. Each job records the
actual client version and per-skill results in its summary and JSON artifact.
Missing skills and discovery errors fail the job. Missing prerequisites are
failures, not successful compatibility checks.

CI also combines the pinned-client results into the README support table,
including failed skill checks. A client setup or global scan failure produces
unverified cells instead of marking every skill unsupported. PRs and branch runs
publish a README preview artifact and table summary. A push to the default branch,
including a merged PR, reruns discovery and refreshes the README table.
CI updates only the generated table in `README.md` with a bot commit. It skips
the write if the branch has moved since the checked revision. Branch rules
apply to that push. Latest-version results remain in the separate job
summaries and artifacts; they do not replace the pinned table.

## Refresh the support table

The table is generated by
[update_agent_support.py](../scripts/update_agent_support.py) between the
`agent-support:start` and `agent-support:end` comments. Its cells require report
provenance and source hashes to match; missing or stale evidence stays
unverified. Maintain the surrounding prose normally and regenerate the table
from discovery reports:

```text
.venv/bin/python scripts/update_agent_support.py --reports /tmp/support-reports --revision <full-commit-sha>
```

Store each report under
`agent-support-<agent>-pinned/agent-support.json` in that directory, using
`codex` and `claude-code` as the agent names. Add `--run-url <actions-run-url>`
for CI reports, or omit it for local reports. Reports from CI carry the tested
commit, channel, and run URL; local evidence is labeled separately.
For local reports, `--revision` labels the base commit; the source hashes bind
the results to the current working tree, including uncommitted package changes.

## Client versions and boundaries

The baseline is Codex CLI `0.161.0` and Claude Agent SDK `0.2.164`, whose bundle
contains Claude Code `2.1.292`. Update the Codex pin in the workflow and the
Claude SDK pin in [requirements-agent-ci.txt](../requirements-agent-ci.txt) after
reviewing an upstream failure. These checks need no API keys: Codex only receives
local discovery requests, and Claude SDK connects without sending a prompt.
They copy sources into isolated project and home directories and do not install
skills into the developer's user profile.

Discovery does not establish invocation-policy parity. Claude Code does not
apply `agents/openai.yaml`; in particular, the explicit-only Codex policy for
`maintain-skills` is not enforced by that file in Claude Code. The
`reflect` skill-editing workflow still requires an available
`skill-creator`; discovery does not test this dependency or the Skills CLI used
by `maintain-skills`. These discovery probes exercise no model decisions,
domain tools, or installation/update operations.

The probes use the official
[Codex app-server protocol](https://developers.openai.com/codex/app-server)
and the Claude SDK's prompt-free `ClaudeSDKClient.connect()` and
`get_server_info()` methods, implemented in the
[official Python SDK](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/client.py).
See also the [Claude SDK skill documentation](https://code.claude.com/docs/en/agent-sdk/skills).

## Local checks

### Setup Fern validation

Use the repository-wide [validation layers](validation.md) on a user machine
through Docker, or through repository CI. Fern is included in the same planner
as the other collections. For a focused local installation check:

```text
python scripts/run_validation.py --layer affected --check fern-install --output /tmp/fern-install-001
```

Use a new absolute output directory outside the checkout and real client
profiles. On Windows, substitute a writable absolute temporary path. The
legacy `scripts/run_fern_validation.py` launcher remains available for existing
Fern-specific calls; the unified launcher is the maintained selection entry.

The installation probe tests real Skills CLI installation from resolved public
snapshots, copied package bytes and source provenance, and fresh Codex user
skill discovery. Its repeat verification is read-only. It does not install the
unpublished candidate or test a second mutating installation. Parsing bundled
agent TOMLs, checking config and embedding instructions do not establish native
custom-agent loading. See the
[behavior procedure](behavior-checks.md#run-setup-fern-in-docker) for actual
model runs and the [Fern cases](../examples/setup-fern.md) for the remaining
manual scenarios.

### Blender regressions

The [Blender collection](../skills/blender/README.md) includes pure-data component
tests and optional background Blender tests. From the repository root, use the
isolated Python environment:

```text
python -m unittest discover -s tests -p test_scene_components.py -v
python -m unittest discover -s tests -p test_scene_blender_integration.py -v
python -m unittest discover -s tests -p test_low_poly_blender_integration.py -v
```

For the two integration suites, set `BLENDER` to the full path of an existing
Blender executable. They create temporary fixtures outside the repository and
launch independent background processes; they do not use an open editor session.
Without that executable, direct unittest discovery reports explicit skips.
The layered Docker runtime supplies Blender for the separate `blender` check;
a requested engine check fails if its executable is unavailable. Layer 1
excludes both real-engine modules rather than counting their skips as engine
coverage. A passing background run still does not validate an editor session.

The suites cover component geometry, example scene construction, scene auditing,
and the low-poly audit's read-only behavior and JSON output. FBX transfer tests
remain in `saberuster/agent-skills` with its Unreal plugin. These checks do not
establish reference fidelity, visual quality, character deformation quality,
Unreal import, or game-runtime correctness.

### Godot helper regressions

The [Godot collection](../skills/godot/README.md) includes isolated regression
tests for its PowerShell runner and log preflight. From the repository root,
use the isolated Python environment:

```text
python -m unittest discover -s tests -p test_godot_build_regressions.py -v
```

The suite requires PowerShell 7.2+ on `PATH`, or an explicit executable in
`PWSH`. Fixtures create temporary Git projects and fake Godot processes to
exercise log boundaries, argument handling, output collection, error reporting,
timeouts, process cleanup, and concurrency. No Godot installation is required.
Unreal and MCP regressions remain in `saberuster/agent-skills`.

Layer 1 includes this suite and supplies PowerShell in Docker. Missing
PowerShell cannot silently satisfy that required check. Direct unittest runs
can still skip missing prerequisites, platform-specific cases or unavailable
symlink privileges; report those gaps separately. Windows-only branches remain
uncovered by a Linux container. The
[native Windows CI](validation.md#native-windows-ci) runs this module alongside
all other non-engine regressions, requires junction
and symlink execution, and records the exact POSIX/Linux exclusions.
Windows and Linux evidence are distinct.
These fixtures do not establish real Godot execution,
scene or asset correctness, UI behavior, or client discovery.

### Static checks and client probes

Run the commands in [Development](../README.md#development) first. The same
pinned dependencies and checks are used locally and by CI.

The package tests use `markdown-it-py` to check inline and reference-style local
links, images, and Markdown heading fragments, including same-page anchors.
Code examples and external URLs are excluded from local target checks.

`package.json` pins `markdownlint-cli2` to `0.23.3`.
`.markdownlint-cli2.jsonc` sets an 80-character prose line limit, exempts code
blocks and tables, and allows repeated headings under different parent headings
with `siblings_only`. It also requires ATX (`#`) headings, dash bullets,
ascending ordered-list numbers, and fenced code blocks using backticks. It
excludes `node_modules`, `.venv`, `.git`, and `.ruff_cache`. Run
`npm run lint:md:fix` to apply fixes supported by the tool.
This command is not a full Markdown formatter and does not guarantee automatic
line wrapping for every violation.

Ruff provides both linting and formatting. Its version is pinned in
`requirements-dev.txt`, which local development and CI both install. Rules in
`ruff.toml` enable basic correctness checks (`E4`, `E7`, `E9`, `F`) and import
sorting (`I`), targeting Python 3.11. To apply formatting, run
`.venv/bin/python -m ruff format .` with the same Windows path substitution.
These dependencies are only for repository development; skill users do not need
to install them.

## Run client discovery locally

Prefer the Docker `codex-discovery` and `claude-discovery` checks in the
[validation layers](validation.md) for user-machine validation. The following
direct commands are debugging entrypoints for the probes themselves.

Use `.venv/bin/python` on macOS/Linux, or `.venv\Scripts\python.exe` on
Windows, from the repository root. Codex must be available on `PATH`;
`--codex` can select a specific executable. The
Claude checker uses the SDK's bundled CLI by default; `--claude` can select an
existing executable instead. Write reports outside the repository:

```text
.venv/bin/python -m pip install -r requirements-agent-ci.txt
.venv/bin/python scripts/check_codex_skills.py --report /tmp/codex-skills.json
.venv/bin/python scripts/check_claude_skills.py --report /tmp/claude-skills.json
```

On Windows, use an absolute report path in a writable temporary directory in
place of `/tmp/...`. Run the Codex discovery probe under Linux or WSL: Windows
Codex can locate user skills through the OS home directory despite temporary
`HOME` and `USERPROFILE` values. The probe fails on that isolation leak; this
does not establish a skill compatibility failure. Claude initialization and
the static checks can run on Windows.

The deterministic PR workflow runs layer 1, while the agent support workflow
records prompt-free discovery for layers 2 and 3. Actual agent behavior uses the
separate runtime/full workflow paths in the [validation guide](validation.md).
For manually delivered [behavioral cases](behavior-checks.md), retain actions
and resulting files as well as evaluator assessments.

Claude discovery errors include the exception type and failure stage. The CLI
version probe has a 15-second timeout; initialization has a 60-second timeout.
A timeout leaves discovery failed and affected skills unchecked, even when the
exception itself has no message.
